## 1. 目的と非目的

### 目的

実卓（リアル麻雀）で使う点数表示器。iPhone 1台を卓上に置き、対局中の持ち点・局・本場・供託・リーチ状態を表示し、点数移動を入力する。あわせて対局結果と局ごとのイベントを蓄積し、成績を集計する。

### 非目的

- 手牌からの役判定・符計算はしない。翻と符は人間が入力する。
- 対局のシミュレーションや戦術支援はしない。
- 複数端末の同期はしない。データは端末内に閉じる。
- 他人と共有しない。単一利用者を前提とする。

---

## 2. 利用シナリオと前提

- 明るい室内、対局中の卓上。片手で、手を止めずに操作する。
- 操作の頻度が高い順に、リーチ宣言、和了入力、副露のカウント。
- 誤タップは必ず起きる。取り消しと修正の経路を常に用意する。
- ネットワークは無い前提で動く。
- 端末は iPhone。ホーム画面に追加した PWA として起動する。

### 端末の配置

3人・4人とも卓中央に縦向きで置く。各パネルはその席の方向に回転させ、各自が自分の位置から正立で読む。

| 画面上の位置 | 相対席 | 回転 |
|---|---|---|
| 下 | 自家 | 0° |
| 右 | 下家 | −90° |
| 上 | 対面 | 180° |
| 左 | 上家 | +90° |

3人麻雀は4箇所のうち1箇所を空席にする。**空席の位置は設定で選ぶ**（実卓でどこが空くかは座り方による）。

## 3. 用語

| 語 | 意味 |
|---|---|
| 局 | 東1局〜南4局。3人麻雀は東1〜東3（東場のみ）または南3まで |
| 席順 | 起家を index 0 とする固定の並び。親は局ごとに回る |
| 供託 | 場に出ているリーチ棒。次の和了者が回収する |
| 局末イベント | `agari` / `ryuukyoku` / `chombo`。局の区切りを作る |
| 有効局 | 局末イベントのうち `chombo` を除いたもの。統計の分母 |
| deltas | 点数移動の配列。再計算可能なキャッシュとして保持する |

## 4. データモデル

### 4.1 原則

**イベント列が唯一の真実とする。** 持ち点・局番号・本場・親・供託・リーチ状態・副露状態はすべて、イベント列を畳み込んで得る導出値であり、状態としては保存しない。

派生する規則:

- **局中の操作もイベントにする。** リーチ・副露・北抜きは点数表示に影響し、かつ「戻す」の対象になる。イベントにしないと、局末イベントが発生するまで状態がイベント列に存在せず、再読み込みで失われる。
- イベントに `kyoku` と `honba` を持たせない。順序だけが意味を持つ。修正で連荘の有無が変われば、局番号は自動で変わる。
- 「一つ戻す」は最後のイベントの削除。専用のスナップショットスタックは持たない。
- **`deltas` は再計算可能なキャッシュとして扱う。** 保存はするが、これを唯一の根拠にはしない。過去のイベントを編集した場合、**編集地点以降のすべての得点イベントの `deltas` を順に再計算する**。編集地点より前は再計算しない。

`deltas` を焼き込む当初の意図は「点数計算を後で修正しても過去の記録が動かない」ことだったが、これは編集機能と両立しない。親と本場が変われば同じ翻符でも移動額が変わるためである。計算ロジックの版を永続化する方式（calcVersion）は、単一利用者の規模に対して保守コストが見合わないため採らない。点数計算に誤りが見つかった場合は、過去の記録も再計算で直る方が望ましい。

### 4.2 保存キー

```
mj.meta     { schemaVersion, updatedAt }
mj.roster   [ { id, name, createdAt } ]
mj.current  Game | null          // 進行中の対局
mj.games    [ Game ]             // 終了した対局（新しい順）
```

プレイヤーは ID で参照する。名前を直接参照すると、改名で履歴が分断される。

### 4.3 Game

```
Game = {
  id: "g_20260905_2130",
  startedAt, endedAt,
  rule: Rule,                    // 対局開始時のルールをスナップショット
  seats: [playerId, ...],        // 起家順。長さ = rule.playerCount
  bottomSeat: seatIndex,         // 画面下（自家）に置く席。表示の回転にだけ使う
  events: [Event, ...],
  settlement: Settlement | null  // 終局時に確定。編集したら null に戻して再計算
}
```

`bottomSeat` は「誰がどこに座っているか」の記録であり、点数計算には関与しない。開始画面で画面位置ごとにプレイヤーを選び、起家の位置から `seats` と `bottomSeat` を導く（v0.7、段階2で追加）。

### 4.4 Event

```
Event =

  // --- 局中の操作 ---
  | { t:"riichi", who }                    // 即時に 1000点供出、供託 +1
  | { t:"meld",   who, value: bool }       // 副露フラグのトグル（暗槓は含めない）
  | { t:"kita",   who, delta: +1 | -1 }    // 北抜き（三麻のみ）。UI からは発行しない（v0.11）。畳み込みは受け付ける

  // --- 局末イベント ---
  | { t:"agari",
      tsumo: bool,
      from: seatIndex | null,              // ロン時の放銃者
      winners: [ Winner, ... ],
      deltas: [int, ...] }

  | { t:"ryuukyoku",
      type: "exhaustive" | "abortive" | "nagashi",
      abortiveKind: "kyuushu" | "suufon" | "suucha_riichi"
                  | "suukaikan" | "sanchaho" | null,
      tenpai: [seatIndex, ...],            // exhaustive のみ意味を持つ
      nagashiBy: [seatIndex, ...],         // nagashi のみ
      deltas: [int, ...] }

  | { t:"chombo", who, deltas }

  // --- その他 ---
  | { t:"adjust", note, deltas }           // 手動修正。非ゼロサムを許す
  | { t:"end" }                            // 手動終局のみ

Winner = {
  who,
  han,                    // 通常手のみ。役満手では未使用
  fu,                     // 同上
  yakumanCount: 0|1|2|3,  // 0 = 通常手。1以上で役満手
  sekinin: { who, yakumanCount } | null,
  chips: int              // 常に 0。チップは扱わない（v0.11）。互換のため残す
}
```

`winners` を配列で持つことで、単独和了・頭ハネ・ダブロンを同じ形で扱う。

局末イベントに `RoundState` を持たせない（v0.4 からの変更）。リーチ・副露・北抜きが独立したイベントになったため、局の状態はイベント列から導出できる。両方を持つと二重管理になる。

`end` の `reason` を廃止した。`normal`（規定局数の消化）と `tobi` は状態から導出できるため、イベントにすると編集後に実態と食い違う。手動終局のみをイベントとして残す。

### 4.5 局の区切り

イベント列は、局末イベントによって局に区切られる。ある局に属するイベントは「直前の局末イベントの次から、当該局末イベントまで」である。

この単位は編集操作でも保たれる必要がある。**ログ画面で局を削除する場合、局末イベントだけでなく、その局に属する `riichi` / `meld` / `kita` / `adjust` をまとめて削除する。** 局末イベントのみを削除すると、局中イベントが前後の局に混入する。

`end` イベントはどの局にも属さない。局の削除で消えない。

## 5. 状態の導出

初期状態からイベントを順に適用し、各時点の状態を得る。

```
State = {
  points[], kyoku, honba, kyotaku, over,
  round: { riichi[], melded[], kita[] }   // 現在局の一時状態
}
```

初期値: `points[i] = rule.startPoints`、`kyoku = 0`、`honba = 0`、`kyotaku = 0`、`round` は全て空。

- 親: `dealer = kyoku % playerCount`
- 自風: `(i - dealer + n) % n`
- 場: `floor(kyoku / playerCount)`（0 = 東場、1 = 南場）
- 局番号: `kyoku % playerCount + 1`

4人麻雀は kyoku 0〜3 が東1〜東4、4〜7 が南1〜南4。3人麻雀は 0〜2 が東1〜東3、3〜5 が南1〜南3。

### 5.1 局中イベント

```
riichi  points[who] -= 1000
        kyotaku += 1
        round.riichi[who] = true

meld    round.melded[who] = event.value

kita    round.kita[who] += event.delta
```

**1000点未満はリーチできない**（`rule.riichiUnderThousand` が偽のとき、既定）。`points[who] < 1000` の者の `riichi` イベントは発行しない。畳み込みはイベントをそのまま適用する（検証は発行時に行う）。真にした場合は持ち点に関係なく発行できる。

リーチは即時に反映する。局末でまとめて処理しない。

### 5.2 agari

```
1. 全 winner 分の deltas を合算し、points へ一括適用する
2. 供託を rule.multiRonKyotaku に従って winners に配分 → kyotaku = 0
     "shimocha": 放銃者から反時計回りに最も近い和了者（ツモなら和了者）が総取り
     "split":    和了者で等分。100点単位で切り捨て、端数は下家取りの者へ
3. 連荘判定:
     親が winners に含まれる → kyoku 据置、honba += 1
     含まれない              → kyoku += 1、honba = 0
4. round をリセット
5. 終局判定
```

**手順1を原子的に行うことが不変条件である。** winner ごとに逐次適用してから判定すると、複数和了で途中の中間状態がトビ線を割る場合に判定が狂う。

### 5.3 ryuukyoku

タイプごとに遷移を分ける。以下は本アプリの採用ルールとして固定する（いずれも流派差のある箇所である）。

**`exhaustive`（通常の流局）**

```
deltas を適用（テンパイ料）
honba += 1
rule.renchan === "tenpai" かつ 親が tenpai に含まれる → kyoku 据置
それ以外                                            → kyoku += 1
round をリセット
```

`rule.renchan === "agari"` を選んだ場合、流局では常に親が流れる。

**`abortive`（途中流局：九種九牌・四風連打・四家立直・四開槓・三家和）**

```
点数移動なし（deltas は全て 0）
honba += 1
kyoku 据置（親は常に連荘。テンパイ判定を行わない）
供託はそのまま場に残す（kyotaku を変更しない）
round をリセット
```

テンパイ・ノーテンの概念を持ち込まない。`tenpai` フィールドは空とする。

**`nagashi`（流し満貫）**

```
nagashiBy の各人に満貫相当の支払いを行う（deltas に反映）
テンパイ料は発生させない
honba += 1
rule.renchan === "tenpai" かつ 親が tenpai に含まれる → kyoku 据置
それ以外                                            → kyoku += 1
```

流し満貫の成立者が複数いる場合、それぞれが独立に満貫を受け取る。連荘の判定は通常の流局と同じくテンパイで行うため、`tenpai` フィールドは `nagashi` でも記録する。

満貫相当の支払いはツモ扱い（親は 4000 オール、子は 2000/4000）。本場は加算しない。3人麻雀はツモ損（北家分を差し引く）。

### 5.4 chombo

チョンボした者が罰符を払い、**その局はなかったことにする**。局を流して同じ局をやり直す。`kyoku` 据置、`honba` 据置。

**その局で出たリーチ棒は宣言者に返却する。**

```
現在局の riichi イベント（round.riichi が true の者）について:
  points[who] += 1000
  kyotaku -= 1
罰符を適用: points[i] += deltas[i]
round をリセット
```

前局までに積まれていた供託は場に残る。

チョンボで流れた局は統計の対象外とする。和了率・放銃率・リーチ率・副露率の分母（有効局）から除外する。局として成立しなかったものとして扱う。

### 5.5 adjust

```
points[i] += deltas[i]
```

`round` には影響しない。局を終了させないため、統計の分母にも影響しない。

**非ゼロサムを許す。** 手動修正は物理点棒とのズレを1タップで直すための導線であり、相手方の指定を強制すると入力コストが倍になる。そのかわり、精算時に卓外との差額として明示する（§7）。入口はメニューの「手動修正」（対象者を選び ±100 / ±1000 をタップ）。

### 5.6 終局判定

局末イベントの適用後に評価する。

```
kyoku >= rule.length                              → over
rule.tobi かつ points に rule.tobiLine 未満がある  → over
end イベントがある                                 → over
```

`over` は導出値であり、保存しない。

**アガリやめは自動で終局させない。** オーラス（`kyoku === rule.length - 1`）で親が連荘し（和了、またはテンパイで据置）、集計後に親がトップであれば、`rule.agariYame` が真のとき **親がやめるかどうかを選べる**。やめる場合は `end` イベントを発行する。続ける場合は何も発行せず次局へ進む。この「選べる状態」は導出値 `agariYameAvailable` として提供し、UI が選択肢を出す。

## 6. 点数計算仕様

### 6.1 基本点

役満手と通常手で計算ルートを分ける。

```
if (winner.yakumanCount > 0) {
    // 役満手。翻・符は使わない
    base = 8000 × (rule.doubleYakuman ? yakumanCount : 1)
} else if (han >= 13) {
    // 数え役満
    base = (rule.kazoeYakuman === "yakuman") ? 8000 : 6000
} else if (han >= 11) { base = 6000 }
  else if (han >= 8)  { base = 4000 }
  else if (han >= 6)  { base = 3000 }
  else if (han === 5) { base = 2000 }
  else {
    base = min(fu × 2^(2+han), 2000)
    if (rule.kiriageMangan && base === 1920) base = 2000
  }
```

役満手か通常手かは `winner.yakumanCount` で判別する。真偽値ではなく個数で持つことで、ダブル役満・トリプル役満と複合役満が同じ形で扱える。

`han >= 13` の分岐を役満手より後に置くことが必須である。先に置くと `kazoeYakuman: "sanbaiman"` が機能しない。

**切り上げ満貫**（`rule.kiriageMangan`、既定は真）。4翻30符（30 × 2⁶）と3翻60符（60 × 2⁵）はどちらも基本点が 1920 になり、2000 未満でこの値をとる組み合わせは他に存在しない。基本点の段階で潰すため、ロンとツモの区別も親子の区別も不要。跳満以上への切り上げには適用しない。

### 6.2 4人麻雀の支払い

各支払いは 100点単位に切り上げる。

```
ロン  親 = ceil100(base × 6)、子 = ceil100(base × 4)
      + 300 × honba を放銃者が負担

ツモ  親  各子から ceil100(base × 2)
      子  親から ceil100(base × 2)、各子から ceil100(base × 1)
      + 100 × honba を各支払者が負担
```

### 6.3 3人麻雀のツモ支払い

**ツモ損ありに固定する。** 設定項目は持たない。

4人麻雀と同じ単価のまま支払者が1人少ないため、その分が和了者の得点から落ちる。子の満貫ツモなら、子から2000・親から4000で、和了者の得点は6000。

```
ツモ  親  各子から ceil100(base × 2)
      子  親から ceil100(base × 2)、子から ceil100(base × 1)
```

4人麻雀の式から北家の支払いを取り除くだけで、支払い計算は共通化できる。

ツモ損なしのルール（総額を4人麻雀に揃える方式）は実装しない。総額を2人で分ける都合で100点単位に割り切れない組み合わせが出るため、丸め規則を別途定義する必要が生じ、それに見合う利得がない。フリー雀荘のツモ損なしルールは表現できない。

### 6.4 テンパイ料

`exhaustive` のみで発生する。

```
テンパイ者が 0人 または 全員 → 移動なし
それ以外 → rule.ryuukyokuTenpaiTotal を テンパイ者で山分けし、
           ノーテン者で等分負担
```

### 6.5 責任払い（包）

役満手（`yakumanCount > 0`）でのみ選択できる。

```
Winner.sekinin = { who: seatIndex, yakumanCount: int }
```

責任者が負担するのは役満全体ではなく、`sekinin.yakumanCount` 個分に相当する額である。複合役満で片方だけに包が成立する場合（大三元は包あり、四暗刻は包なし）を表現するために必要である。

```
責任分の基本点 = 8000 × sekinin.yakumanCount
非責任分       = base − 責任分

ツモ  責任分は責任者が全額を負担
      非責任分は通常のツモ配分に従う

ロン  rule.sekininRon = "half" → 責任分を責任者と放銃者で折半
                       "full" → 責任分を責任者が全額

本場  ロン: 放銃者が 300×本場 を負担する。責任者は本場を負担しない
      ツモ: 和了者以外の全員が通常の支払者として 100×本場 を負担する（責任者も含む）。
           責任分には本場を上乗せしない
責任分の上限  責任分の基本点は base を超えない（rule.doubleYakuman が偽のときに効く）
折半の丸め  責任者側を切り上げ、放銃者側を残余とする（100点単位）
```

### 6.6 複数和了

`rule.multiRon` が偽なら頭ハネ（放銃者から反時計回りに最も近い者のみ和了）。真なら全員が和了する。

供託の帰属は `rule.multiRonKyotaku`、本場の帰属は `rule.multiRonHonba` に従う。既定はどちらも下家取り（放銃者から反時計回りに最も近い和了者が総取り）。`multiRonHonba: "each"` を選んだ場合、放銃者は本場分を和了者の人数分だけ支払う。

頭ハネの絞り込みは入力時ではなく畳み込み時に行う。イベントには和了を申告した全員を `winners` に残し、点数計算と連荘判定（§5.2）は絞った後の和了者で行う。ルールを後から変えても記録が壊れない。

### 6.7 チョンボ

`rule.chomboRule` で方式を選ぶ。

```
"mangan"   満貫払い。チョンボ者が以下を支払う
             親の場合: 各子に 4000 ずつ
             子の場合: 親に 4000、各子に 2000 ずつ
           3人麻雀では北家分を差し引く（ツモ損と同じ扱い）
"manual"   チョンボ入力画面で deltas を直接指定する
```

既定は `"mangan"`。`chomboPenalty: 8000` という単一の数値は、支払いの配分方法を定義できないため廃止した。

`"manual"` の `deltas` はそれ自体が意味情報であり、編集後の再計算（§8.4）でもそのまま保持する。

競技ルールでは対局中の点棒移動ではなく最終ポイントからの減算とする例もあるが、本アプリでは扱わない。必要なら `"manual"` か `adjust` で処理する。

## 7. ルール設定

全項目をデータとして持つ。設定 UI はプリセットの選択と、頻繁に変える数項目のみを出す。残りは JSON を直接編集して反映させる。

```
Rule = {
  // 卓
  playerCount: 4,               // 3 | 4
  length: 8,                    // playerCount または playerCount × 2 のみ
  startPoints: 25000,
  returnPoints: 30000,
  uma: [20, 10, -10, -20],      // 長さ = playerCount。合計は必ず 0

  // 進行
  renchan: "tenpai",            // tenpai | agari
  agariYame: true,
  tobi: true,
  tobiLine: 0,
  abortiveRyuukyoku: ["kyuushu","suufon","suucha_riichi","suukaikan","sanchaho"],
  nagashiMangan: false,
  riichiUnderThousand: false,

  // 点数
  kuitan: true,
  akaDora: 3,
  kiriageMangan: true,
  kazoeYakuman: "yakuman",      // yakuman | sanbaiman
  doubleYakuman: true,
  multiRon: true,
  multiRonKyotaku: "shimocha",  // shimocha | split
  multiRonHonba: "shimocha",    // shimocha | each
  sekinin: true,
  sekininRon: "half",           // half | full
  ryuukyokuTenpaiTotal: 3000,
  chomboRule: "mangan",         // mangan | manual

  // 3人麻雀のみ（ツモ損ありは固定。設定項目を持たない）
  emptySeat: "left",            // left | right | top

  // 終局
  finalKyotaku: "top",          // top | remain

  // 精算
  rate: 50,                     // 1pt あたりの円
  rateBase: "point",            // point | rawScore（rawScore は (points − startPoints)/1000 × rate。暫定）
  ptRounding: "round5"          // 五捨六入。"none" なら小数のまま
}
```

### 制約

起動時に検証する。

```
sum(rule.uma) === 0
rule.uma.length === rule.playerCount
rule.length === rule.playerCount || rule.length === rule.playerCount × 2
```

`length` を任意の値にしても §5 の場・局番号の導出式は破綻しないが、「東1〜南4」という用語定義と矛盾するため制限する。

### プリセット

| 名前 | playerCount | length | 持ち点/返し | uma |
|---|---|---|---|---|
| 4人標準 | 4 | 8 | 25000 / 30000 | 20 / 10 / −10 / −20 |
| 3人標準 | 3 | 6 | 35000 / 40000 | 30 / −10 / −20 |

その他の項目は既定値のまま。

### 精算

```
順位   持ち点の多い順。同点なら起家に近い者（seats の index が小さい方）を上位とする

pt(i) = 丸め((points[i] - returnPoints) / 1000) + uma[rank(i)]
        + (rank(i) === 0 ? オカ : 0)

オカ = (returnPoints - startPoints) × playerCount / 1000

円(i) = pt(i) × rate
```

**丸め（`ptRounding`）。** 既定は `"round5"`（五捨六入）: 点差の下 3桁が 500 以下なら切り捨て、600 以上なら切り上げ。負数は絶対値で丸めて符号を戻す（2,500 → 2、2,600 → 3、−2,500 → −2、−2,600 → −3）。五捨六入では合計が 0 に閉じないため、**トップの pt は他の合計の符号反転**とし、丸めの端数とオカをトップが引き受ける。`"none"` は小数のまま持ち、上の式をそのまま使う。

チップは扱わない（v0.11）。

### ゼロサムの条件

pt の合計が 0 になるのは、次の3つが揃った場合のみである。

1. `sum(uma) === 0`（上記の制約で保証する）
2. 終局時の供託が 0
3. `adjust` の合計が 0

**終局時に残った供託の扱いを `rule.finalKyotaku` で定める。** 既定は `"top"`（トップの持ち点に加算）。これを選ぶと条件2が自動で満たされ、精算がゼロサムに閉じる。`"remain"` を選ぶと供託が場に残ったまま終局し、pt の合計は供託本数分だけマイナスになる。

`adjust` は非ゼロサムを許すため（§5.5）、条件3は保証されない。**結果画面に「卓外差額」として `sum(全 adjust の deltas)` を明示する。** 差額が 0 でない場合、「誰が誰にいくら払うか」の経路計算は差額を卓外への支払い（または卓外からの受取）として扱う。

### 8.2 対局画面

**プレイヤーパネルの構成**（席の方向に回転させる）

```
   [リーチ]  [副露]           ← 絵のみの大ボタン。文字を置かない
 ┌──────────────────────┐
 │ 東 起家              │
 │      35,000    [+/−] │   ← 黒地・黄色数字。本体タップで和了入力。+/− は点差表示
 └──────────────────────┘
```

北抜きのボタンは置かない（v0.11）。三麻でも操作はリーチ・副露・和了入力だけで足りる。

- 黒地に黄色の数字。実物の点数表示器の見え方に合わせ、緑の卓面に対して視認性を確保する
- **パネル本体のタップで和了入力を開く**。面積を大きく取る
- リーチ・副露はそれぞれ即座にイベントを発行する。「戻す」で1つずつ取り消せる
- **リーチボタンの再タップでリーチを解除する。** 現在局にあるその席の `riichi` イベントを削除し、以降を再計算する（イベント列に「取り消し」を残さない）
- `+/−` はパネル内に常設し、**押した人と他の人との点差**（自分 − 相手）をそのパネルに表示する。点数は動かさない。もう一度押すか、本体をタップするか、一定時間で通常表示に戻る
- 手動修正（`adjust`）はメニューから行う
- 誤タップ対策として、和了入力は確定を押すまで点数を動かさない

**中央・周辺**

| 位置 | 機能 |
|---|---|
| 上部 | 局名・本場・供託（リーチ棒を本数分描画） |
| 左上 | ログ画面への入口。経過時間を併記 |
| 右上 | 戻す（最後のイベントを削除） |
| 中央 | 特殊終局（流局・途中流局・流し満貫・複数和了・チョンボ・手動修正）。流し満貫は `rule.nagashiMangan` が真のときだけ出す。途中流局の種別は `rule.abortiveRyuukyoku` から選ぶ |
| 右下 | メニュー（手動修正、対局終了、設定） |

「戻す」で局末イベントを削除した場合、その局の `riichi` / `meld` / `kita` イベントは残るため、局が再開した状態に戻る。これは意図した挙動である。

### 8.3 和了入力（通常ルート）

```
和了者のパネルをタップ
  → シート1枚に ツモ/ロン、放銃者、翻、符 を配置
  → 翻符の選択と同時に点数をプレビュー
  → 「役満」を選んだ場合は符をスキップし、
     役満の個数（1〜3）と責任払いの選択に切り替え
  → 確定 → 次局
```

翻の選択肢は 1〜4 と、5翻以上は名称（満貫・跳満・倍満・三倍満・数え役満）で提示する。名称は `han` に 5 / 6 / 8 / 11 / 13 として記録する。「役満」は翻の選択肢の1つとして提示し、選ぶと `yakumanCount` の入力に移る。数え役満（13翻以上）は通常手として扱われ、`yakumanCount` は 0 のままである。

**画面をがたつかせない。** 放銃者・翻・符の行は常に同じ位置に描画し、使わない行は無効化して残す。符の行と役満の詳細（個数・包・責任分）は同じ高さのスロットに入れ、シートの高さは固定する。プレビューは常に全員分の行を出す。

複数和了はこのルートに載せない。「特殊終局」から入る。

### 8.4 ログ画面

対局の局一覧。各行に 局・本場・内容・点数移動・その局末の全員の持ち点 を表示する。

- 行をタップして「編集」「前に挿入」「削除」を選ぶ
- 編集は局末イベントの種類に応じたシート（和了入力・複数和了・流局・途中流局・流し満貫・チョンボ）を、既存の値を初期値にして再利用する。シートに渡す状態は、その局末イベントを適用する前の状態
- 挿入は選んだ局の先頭（局中イベントより前）に局末イベントを1つ挟む。進行中の局を選んだ場合は末尾（`end` の前）
- 終了した対局も開始画面の一覧から同じ画面で修正できる。保存先は `mj.games` の該当対局

**編集時の再計算**

```
1. 編集地点より前のイベントはそのまま
2. 編集地点以降のすべての得点イベント（agari / ryuukyoku / chombo）について、
   保存された意味情報（winners の翻符、tenpai、tsumo、from など）から
   deltas を順に再計算する
   親と本場が変わると同じ翻符でも移動額が変わるため、これは必須である
3. adjust の deltas は意味情報を持たないため再計算しない。そのまま保持する
4. settlement を null にして再計算する
```

**局の削除**

局末イベントだけでなく、その局に属する `riichi` / `meld` / `kita` / `adjust` をまとめて削除する（§4.5）。局末イベントのみを削除すると、局中イベントが前後の局に混入する。

**整合性**

修正の結果、局番号が半荘の長さに対してずれる（南4局に届かない、超える）ことを許容する。整合性は強制せず、続きを入力できる状態にとどめる。

### 8.5 成績画面

対局レベル: 対局数、平均順位、順位分布、平均素点、通算 pt、通算金額。

局レベル（有効局を分母とする）: 和了率、放銃率、リーチ率、副露率、平均和了打点、平均放銃打点。

チョンボで流れた局は分母に含めない。表示では対局数を必ず併記する。実卓の対局数では順位率のような指標は統計的にほとんど意味を持たないため、断定的な見せ方をしない。

指標の定義（`src/stats.js`）:

- 和了率 = 和了した局数 / 有効局。複数和了は絞った後の和了者で数える
- 放銃率 = 放銃した局数 / 有効局
- リーチ率 = その局に `riichi` イベントがある局数 / 有効局
- 副露率 = 局末時点で副露フラグが立っている局数 / 有効局
- 平均和了打点 = 和了時の `deltas[who]` の平均（供託は含めない）
- 平均放銃打点 = 放銃時の `−deltas[from]` の平均
- 順位・pt・金額は各対局の `settlement` から取る（無ければ再計算）

### 8.6 結果画面

終局時に精算を計算して `settlement` に焼き込み、結果画面を出す。順位・素点・pt・金額・支払い経路（貪欲法で最小回数）・内訳（レート、ウマ、オカ、残り供託の扱い、卓外差額）を表示し、ログへの入口とエクスポートへの誘導を置く。終了した対局は開始画面の一覧から結果画面を開ける。ログで編集すると `settlement` は null に戻り、次に結果画面を開いたときに再計算して保存する。

### 8.7 バックアップ

開始画面と結果画面から、全データ（meta / roster / current / games）を JSON でエクスポートする。共有シート（`navigator.share` でファイル共有）が使えればそれを使い、なければダウンロードリンクを使う。インポートはファイル選択で JSON を読み、内容を確認したうえで全データを置き換える。`schemaVersion` がアプリより新しいものは拒否する。

### 8.8 成績画面

開始画面から入る。対局レベルと局レベルの表を出し、対局数を併記する。

## 9. 永続化

### 9.1 保存先

localStorage。データ量は数KB〜数MB で、構造化クエリも不要なため IndexedDB は使わない。同期 API のほうがコードが単純になる。

局中操作をイベント化したことで1半荘あたりのイベント数は増えるが、それでも JSON で 4〜8KB 程度。5MB 枠に対して数百半荘が入る。

### 9.2 書き込みタイミング

- `mj.current`: イベント確定ごとに全上書き
- `mj.games`: 終局時に1件追記
- `mj.roster`: プレイヤー追加・改名時

### 9.3 消失リスク

iOS Safari の ITP は、そのサイトへの操作が7日間ないと IndexedDB・LocalStorage・SessionStorage・Service Worker の登録とキャッシュを削除する。この7日はカレンダーではなくブラウザを使った日数のカウント。

**ホーム画面に追加した Web アプリの第一パーティドメインはこのキャップの対象外**であり、データも Safari 側と分離される。したがって PWA として使う限りは残る。Safari のタブで開いたまま使うと消える可能性がある。

残る消失経路: 設定からの「Web サイトデータを消去」、ホーム画面からの削除、機種変更、ストレージ逼迫時のパージ。

### 9.4 対策

- JSON のエクスポートとインポートを常設機能とする。終局時にエクスポートへ誘導する
- `schemaVersion` を持ち、片方向のマイグレーション関数を用意する。過去のマイグレーションは削除しない

## 10. 非機能要件

| 項目 | 要件 |
|---|---|
| オフライン | Service Worker により完全にオフラインで動作する |
| 起動 | 起動から操作可能まで 1秒以内。外部依存を持たない |
| 誤操作耐性 | 全操作が「戻す」で取り消せる。確定前は点数を動かさない |
| 画面の向き | iOS では向きを固定できない（`screen.orientation.lock()` は Safari／iOS Safari とも未対応、ホーム画面 PWA は manifest の `orientation` を無視、Fullscreen API は iPhone で使えない）。CSS で向きを検出し、想定と違う向きのときは案内を表示する |
| スリープ | 対局中は Screen Wake Lock で画面を維持する（iOS 16.4 以降で利用可能） |
| データ保護 | 通信を一切行わない。全データは端末内 |

### 配信

GitHub Pages。静的ファイルのみで動作するため、ブランチ直接配信で足りる。HTTPS が自動で付くため Service Worker が使える。

Service Worker のキャッシュ名にはバージョンを埋める。`skipWaiting` は使わず、更新は次回起動時に適用する（対局中の入れ替わりを防ぐ）。アプリ内に版番号を表示する。

**版番号は `version.js` が唯一の定義。** ES Modules ではなく `self.APP_VERSION = "..."` を置く classic script とし、ページは `index.html` の `<script src="version.js">` で、Service Worker は `importScripts("./version.js")` で同じファイルを読む。更新時はこの1箇所だけ上げる。

Service Worker（`sw.js`）は起動に必要なファイルを install 時にすべて事前キャッシュし、同一オリジンの GET はキャッシュ優先で返す。activate で古い版のキャッシュを消す。登録は `src/ui/app.js` の末尾で行い、失敗しても動作には影響しない（オフラインで開けないだけ）。

manifest（`manifest.webmanifest`）は `start_url` と `scope` を `./` にし、リポジトリ名に依存しない。アイコンは `icons/` に PNG（180 / 192 / 512、maskable）を置く。iOS は `apple-touch-icon` を使う。

公開範囲について: GitHub Free は public リポジトリからのみ配信可能。Pro なら private リポジトリからも配信できるが、**サイト自体は誰でも開ける**。サイトへのアクセス制限は Enterprise Cloud のみの機能。本アプリはデータを端末内に閉じるため、公開されるのはコードのみで実害はないと判断する。エクスポートした JSON はリポジトリに入れない。
